## Credential handling and endpoint integration

The server entry point `@captiondoor/integrations` exports Node/AWS code. The browser uses only a lazy import of `packages/integrations/src/browser-ring.ts`; never import the server entry point from a client component.

`RingClient.createWhepSession` returns an **internal** record containing the Ring Location URL. Persist that record in CaptionDoorRuntime under its opaque `id`, authorize the household/current handler/media lease on every start/close call, and return only `{mediaSessionId: id, answer, expiresAt}` to the browser. Do not put Ring URLs/tokens into public responses, query strings, logs or browser storage. Revocation/expiry must fence existing sockets and media, not only the next login.

For local real-token testing, explicitly set `CREDENTIAL_ENCRYPTION_MODE=development` and provide `DEV_CREDENTIAL_KEY` as a separately generated 32-byte Base64 value in an ignored local environment file. Generate/store it directly in a protected ignored file or approved secret store during a separately authorized setup; no command that echoes a credential is provided here. Never paste it into screenshots or logs. This key protects dev ciphertext only; losing it requires re-linking. Production requires `CREDENTIAL_ENCRYPTION_MODE=kms`, `RING_KMS_KEY_ID`, authorized AWS credentials and `AWS_REGION`. The KMS encryption context binds ciphertext to CaptionDoor/Ring/household/integration. No default credential key exists.

The server HTTP handler owns persisted OAuth state, single-use consume, authenticated membership/CSRF, encrypted credential writes and account/device mapping. The adapter never infers a household from visitor timing, a supplied user ID or a public QR. The app must never report a successful link solely because a token exchange returned.

## Cleanup credential boundary

A live media Runtime record retains a separate encrypted, access-token-only cleanup envelope with no refresh token. Its payload is scoped to `WHEP_DELETE`, the opaque app session, selected device and a maximum 60-second validity (the application currently uses the conservative 30-second provider duration). Unlink removes Config credentials atomically. The cleanup handler uses only this envelope for an allowlisted session DELETE and never refreshes or rewrites Config credentials. The row/copy is explicitly deleted after successful cleanup or after provider expiry; worker/database outages can delay physical removal, with TTL as backstop. This limit is access validity, not a false assertion of exact physical deletion.

Ring integration tests now use dedicated `CaptionDoorRingTestConfig`, `CaptionDoorRingTestVisits` and `CaptionDoorRingTestRuntime` tables on DynamoDB Local. This prevents the running application worker from dispatching mock-provider jobs. The test process alone handles mocked provider calls; no real Ring endpoint is contacted. A WHEP201 response is signaling acceptance only: the persisted visit stays CONNECTING until the browser reports a connected peer with an incoming video track via the authorized ready endpoint. The test supplies that signal explicitly; actual Ring tracks remain unobserved.

Browser readiness regression: `node_modules/.bin/vitest run tests/unit/browser-ring.test.ts` passed **3/3 tests** using mocked RTCPeerConnection/MediaStream and fake timers only. An early video track with ICE still unconnected must time out with cleanup and never report LIVE; a connected peer with no video remains CONNECTING then unavailable; missing optional audio is reported only after both peer connection and video exist. This is a pure code-boundary test, not physical WebRTC/device evidence.

## Credential-free judge replay

The [organizer's replay guidance](https://amazonappdev2026.devpost.com/forum_topics/45541-ring-playground-replay-mode-for-judging-ring-media-in-public-videos-and-simulated-alexa-wording) permits a replay default and says judges should not be required to supply their own Playground token. A replay backed by earlier actual authorized Ring validation must identify that original evidence. CaptionDoor currently has **no recorded actual Ring validation**: its replay is a LOCAL fixture journey through the real application, sockets and DynamoDB Local, not a replay of captured Ring provider behavior. It does not close the substantial-actual-Ring-use gap.

```sh
corepack pnpm judge:replay --help
corepack pnpm judge:replay
# Optional visible browser, same LOCAL provenance:
corepack pnpm judge:replay --headed
```

No provider credentials are required. A healthy isolated local Docker/DynamoDB/web3410/worker3411 environment and Chromium are required; this is not a static or in-memory substitute. The runner refuses existing active demo visits: close them deliberately through the UI before another attempt. Each run writes `output/judge-replay/<UTC timestamp>-<id>/result.json`. Bounded local-health preflight failure records **BLOCKED** and exits2; it is not a browser pass. Only a successful actual child browser journey supplies PASS, with `report/index.html`, `journey-observations.json` and screenshots in that run directory.

The final actual attempt at `output/judge-replay/2026-10-22T02-19-27-994Z-0ed445/result.json` recorded **PASS, exit0**, with1 browser journey passed in 12.4s. The earlier blocked attempt and guarded active-visit refusal remain recorded in [test-results.md](test-results.md). Only LOCAL/FIXTURE behavior is established; no real Ring or AWS observation is implied. Services are intentionally stopped after verification for sequential handoff.
