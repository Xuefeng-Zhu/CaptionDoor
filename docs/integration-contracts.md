## Ring protocol boundary

The [current Ring API](https://developer.amazon.com/docs/ring/api-documentation.html) defines these server-side operations:

| Purpose       | Contract                                                                                                                                                                                                                                                                                                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API origin    | `https://api.amazonvision.com`                                                                                                                                                                                                                                                                                                                                                         |
| Discovery     | `GET /v1/devices`; `GET /v1/devices/{id}?include=capabilities,status`                                                                                                                                                                                                                                                                                                                  |
| Refresh       | Form `POST https://oauth.ring.com/oauth/token`: `grant_type=refresh_token`, `refresh_token`, `client_id`, `client_secret`; replace rotated tokens, honor `expires_in`.                                                                                                                                                                                                                 |
| Partner OAuth | `https://account.ring.com/account/integrations/partner-link/authorize`; code flow, PKCE S256, session-bound random `state`, exact registered HTTPS redirect. Token exchange uses `grant_type=authorization_code`, `code`, `code_verifier`, client credentials. Finalize with `PATCH /v1/accounts/me/app-integrations`, `status: completed`, masked authenticated `account_identifier`. |
| Webhook       | Verify `X-Signature: sha256=<hex>` using partner HMAC-SHA256 key over **raw bytes**, constant time, before JSON parsing. v1.1 `meta.account_id`, `request_id`; `data.type=button_press`, `data.id`, `attributes.source`, epoch-ms `timestamp`. Persist before 2xx within five seconds; persistence error requires 5xx.                                                                 |
| WHEP          | `POST /v1/devices/{id}/media/streaming/whep/sessions`, Bearer, `application/sdp`; require 201, SDP answer and Location. DELETE validated stored Location. Required video, optional audio, `recvonly`; battery 30 seconds, line power 60 seconds.                                                                                                                                       |

CaptionDoor policy: backend owns credentials and signaling; browser receives opaque app media IDs. Allowlist origin/path for returned Locations. Public QR sessions are unrelated to Ring identity. No outgoing speaker audio. Local fixtures never become Ring events through fallback.

## Changes that supersede older examples

The [release notes](https://developer.amazon.com/docs/ring/release-notes.html) available at verification list September 21, 2026 as the latest entry. September 16 documents TAKE/E2EE changes. September 15 adds `DELETE /v1/accounts/me/app-integrations` for partner-initiated OAuth apps; one-way linking returns 403. August 13 introduces invitation-only partner-initiated OAuth. July 21 describes private apps with up to five allowlisted accounts. These changes are documentation evidence, not evidence that this project/account has access.

The [Developer FAQ](https://developer.amazon.com/docs/ring/developer-faq.html) says TAKE initially leaves devices visible while encrypted video is unusable by partners; E2EE devices are absent. Read `configurations.e2e_encryption.enabled` before processing. Device capabilities are read-only, not promises of device control. Show unavailable access honestly and never recommend disabling encryption.

The [official hello-world repository](https://github.com/AmazonAppDev/ring-api-helloworld) demonstrates discovery and WHEP with short-lived Playground tokens (about 30 minutes), or a refresh token plus client credentials. Its README webhook Bearer-secret description conflicts with current HMAC documentation; HMAC wins. No sample code or assets were copied into CaptionDoor by this research.

The [content policy](https://developer.amazon.com/docs/ring/content-policy.html) requires affirmative consent for collection/use/sharing, minimization, accessible withdrawal/account deletion, and deletion across copies/downstream recipients. Biometric recognition and surveillance receive additional scrutiny. CaptionDoor excludes identification, profiling, autonomous reception, and recording. Provider/backup deletion limits must be disclosed; no success claim may conceal pending deletion.

## DynamoDB

The [transaction contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html) permits up to 100 distinct-item actions and 4 MB per atomic transaction in one account/Region. Two actions cannot target the same item: put the condition on the Update instead of pairing ConditionCheck and Update. GSI/Streams propagation can interleave transaction records. Application idempotency items outlive the API's short client-token window; do not rely on stream transaction grouping.

The [read consistency contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) supports strong reads on base tables/LSIs, not GSIs or Streams. Authorize and resolve conflicts from strongly read base items. GSI lookup is discovery only; recheck authoritative items.

The [TTL contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html) uses numeric epoch seconds and delayed cleanup, usually days. Expired items can still exist and be modified. Enforce application expiry before reads, writes and socket operations; explicit deletion jobs remove content, TTL is a backstop.

The [Lambda/Streams contract](https://docs.aws.amazon.com/lambda/latest/dg/with-ddb.html) is at least once and can duplicate records. Use idempotent dispatch, partial batch responses and bounded retries. CaptionDoor's cloud transport design is KEYS_ONLY Runtime job inserts → filtered Lambda → SQS containing job keys → Node worker. Local due-index polling exercises the same durable handler but does **not** validate AWS Streams, Lambda or SQS transport. The persistent job and due GSI recover missed dispatch; Streams is not a permanent queue.

## Transcribe and audio

[Streaming input](https://docs.aws.amazon.com/transcribe/latest/dg/streaming.html) supports signed PCM16 little-endian (not WAV), FLAC, or Opus in Ogg; recommends uniform 50–200 ms chunks and an accurate sampling rate. CaptionDoor selects incoming remote audio only, resamples to mono 16 kHz and sends 100 ms PCM chunks (3,200 bytes). No resident microphone, WAV headers or WebM relabeling. An AWS stream requires credentials/Region and `transcribe:StartStreamTranscription`; the local fixture is separately labeled.

[Partial results](https://docs.aws.amazon.com/transcribe/latest/dg/streaming-partial-results.html) revise during recognition; `IsPartial=false` denotes final segments, not verified truth. CaptionDoor replaces by `(mediaSessionId, ResultId)`, retains offsets/source and persists only finals once. No invented speaker/confidence, no language-model rewriting. Disconnect/lease loss stops the stream and discards delayed buffered audio.

## Web Push and PWA

[WebKit's February 16, 2023 article](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) establishes Web Push on iOS/iPadOS 16.4 Home Screen web apps with permission requested from a direct user action. Feature-detect; offer install/permission guidance. Provider acceptance is not display or user acknowledgement. Browser/device delivery, Focus interaction and hardware compatibility need real-device testing. Cache only a public shell; never transcripts, private API responses, media, tokens or session-bearing pages.

## Hackathon evidence gate

The [official rules](https://amazonappdev2026.devpost.com/rules), rechecked 2026-10-22, list October 23, 2026 at noon PDT as the deadline and require runtime Ring technology and a working demonstration. The [event FAQs](https://amazonappdev2026.devpost.com/details/faqs) name Ring Developer Playground as an acceptable simulator; physical hardware is optional. The [organizer's self-built-simulator clarification](https://amazonappdev2026.devpost.com/forum_topics/45511-ring-track-does-simulator-include-one-i-wrote-myself) also accepts participant-built simulation when substantial actual Ring technology is used. Its example described real-token API validation together with simulated event delivery through the production backend. It does not define a numerical threshold or let mock-only tests prove actual provider use. The [mixed-footage clarification](https://amazonappdev2026.devpost.com/forum_topics/45462-simulator-on-amazon-ring) permits clearly attributed Playground and participant-owned scenarios.

CaptionDoor's implemented adapter, LOCAL fixtures and intercepted-provider tests are engineering evidence; **actual Ring API use has not been observed**. Its self-built simulator could be part of an acceptable mixed demonstration after substantial actual Ring runtime use is evidenced. An official-simulator-only requirement is not asserted. Preserve event, media and transcript provenance separately and never call mixed fixture/provider evidence an unobserved end-to-end Ring caption result. [WHEP](https://developer.amazon.com/docs/ring/api-documentation.html#whep-live-video-streaming) requires video, permits optional incoming audio, and requires all offered tracks to be `recvonly`; no outgoing speaker path exists.

The user's latest instruction authorizes creating/pushing a private GitHub source repository under verified `Xuefeng-Zhu`; Repository execution/private-visibility evidence is recorded in [test-results.md](test-results.md). Public visibility, reviewer invitations, external deployment, public video publication and submission remain unauthorized. Source access for judging, a truthful short demo, product feedback, rights and eligibility remain separate readiness gates.

## Credential-free judge replay

The [organizer's replay guidance](https://amazonappdev2026.devpost.com/forum_topics/45541-ring-playground-replay-mode-for-judging-ring-media-in-public-videos-and-simulated-alexa-wording) permits a replay default and says judges should not be required to supply their own Playground token. A replay backed by earlier actual authorized Ring validation must identify that original evidence. CaptionDoor currently has **no recorded actual Ring validation**: its replay is a LOCAL fixture journey through the real application, sockets and DynamoDB Local, not a replay of captured Ring provider behavior. It does not close the substantial-actual-Ring-use gap.

```sh
corepack pnpm judge:replay --help
corepack pnpm judge:replay
# Optional visible browser, same LOCAL provenance:
corepack pnpm judge:replay --headed
```

No provider credentials are required. A healthy isolated local Docker/DynamoDB/web3410/worker3411 environment and Chromium are required; this is not a static or in-memory substitute. The runner refuses existing active demo visits: close them deliberately through the UI before another attempt. Each run writes `output/judge-replay/<UTC timestamp>-<id>/result.json`. Bounded local-health preflight failure records **BLOCKED** and exits2; it is not a browser pass. Only a successful actual child browser journey supplies PASS, with `report/index.html`, `journey-observations.json` and screenshots in that run directory.

The final actual LOCAL attempt at `output/judge-replay/2026-10-22T02-19-27-994Z-0ed445/result.json` recorded **PASS, exit0** after one browser journey in 12.4s. The final 12-case browser suite also passed. Earlier blocked/guard-refusal attempts remain in [test-results.md](test-results.md). The approved normal Docker restart recovered services; they are now intentionally stopped for sequential handoff. This pass establishes no real Ring or AWS observation.

A future provider-backed replay should preserve sanitized evidence of the original actual Ring operations and label every synthetic event/media/transcript separately; it must not embed tokens, cookies, raw signaling or private visitor content. Current CaptionDoor artifacts contain no such actual Ring validation. The replay clarification is not evidence that LOCAL-only fixtures satisfy the track's actual-technology requirement. [Ring smoke preparation](ring-smoke.md) and [tool feedback](tool-feedback.md) remain documentation, not executed provider operations.
