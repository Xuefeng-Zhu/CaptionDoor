## Ring protocol boundary

The [current Ring API](https://developer.amazon.com/docs/ring/api-documentation.html) defines these server-side operations:

| Purpose       | Contract                                                                                                                                                                                                                                                                                                                                                                               |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API origin    | `https://api.amazonvision.com`                                                                                                                                                                                                                                                                                                                                                         |
| Discovery     | `GET /v1/devices`; `GET /v1/devices/{id}?include=capabilities,status`                                                                                                                                                                                                                                                                                                                  |
| Refresh       | Form `POST https://oauth.ring.com/oauth/token`: `grant_type=refresh_token`, `refresh_token`, `client_id`, `client_secret`; replace rotated tokens, honor `expires_in`.                                                                                                                                                                                                                 |
| Partner OAuth | `https://account.ring.com/account/integrations/partner-link/authorize`; code flow, PKCE S256, session-bound random `state`, exact registered HTTPS redirect. Token exchange uses `grant_type=authorization_code`, `code`, `code_verifier`, client credentials. Finalize with `PATCH /v1/accounts/me/app-integrations`, `status: completed`, masked authenticated `account_identifier`. |
| Webhook       | Verify `X-Signature: sha256=<hex>` using partner HMAC-SHA256 key over **raw bytes**, constant time, before JSON parsing. v1.1 `meta.account_id`, `request_id`; `data.type=button_press`, `data.id`, `attributes.source`, epoch-ms `timestamp`. Persist before 2xx within five seconds; persistence error requires 5xx.                                                                 |
| WHEP          | `POST /v1/devices/{id}/media/streaming/whep/sessions`, Bearer, `application/sdp`; require 201, SDP answer and Location. DELETE validated stored Location. Required video, optional audio, `recvonly`; battery 30 seconds, line power 60 seconds.                                                                                                                                       |

CaptionDoor policy: backend owns credentials and signaling; browser receives opaque app media IDs. Allowlist origin/path for returned Locations. Public QR sessions are unrelated to Ring identity. No outgoing speaker audio. Local fixtures never become Ring events through fallback.

## Changes that supersede older examples

The [release notes](https://developer.amazon.com/docs/ring/release-notes.html), rechecked on October 22, 2026, now list October 22 as the latest entry. The new one-way-link clarification says the initial Token Exchange URL receives a form POST with `code` and `client_id`, without a verifiable signature; acknowledge only after code exchange and durable token storage, because a non-2xx response fails the link and Ring does not retry. The later browser-redirect HMAC nonce binding remains separate. Each refresh invalidates the previous refresh token. October 12 adds location relationships to subscription coverage alongside device relationships; October 9 clarifies encryption booleans. The web reader returned a newer release-note snapshot than the API-page snapshot; these newly published clarifications supersede the older snapshot. September 16 documents TAKE/E2EE changes. September 15 adds `DELETE /v1/accounts/me/app-integrations` for partner-initiated OAuth apps; one-way linking returns 403. August 13 introduces invitation-only partner-initiated OAuth. July 21 historically describes private apps with up to five allowlisted accounts; the current Developer FAQ Q15/Q16 now specifies up to ten, so ten is the current documented private-account limit. These changes are documentation evidence, not evidence that this project/account has access.

The [Developer FAQ](https://developer.amazon.com/docs/ring/developer-faq.html) says TAKE initially leaves devices visible while encrypted video is unusable by partners; E2EE devices are absent. Read `configurations.e2e_encryption.enabled` before processing. Device capabilities are read-only, not promises of device control. Show unavailable access honestly and never recommend disabling encryption.

The [official hello-world repository](https://github.com/AmazonAppDev/ring-api-helloworld) demonstrates discovery and WHEP with short-lived Playground tokens (about 30 minutes), or a refresh token plus client credentials. Its README webhook Bearer-secret description conflicts with current HMAC documentation; HMAC wins. No sample code or assets were copied into CaptionDoor by this research.

The [content policy](https://developer.amazon.com/docs/ring/content-policy.html) requires affirmative consent for collection/use/sharing, minimization, accessible withdrawal/account deletion, and deletion across copies/downstream recipients. Biometric recognition and surveillance receive additional scrutiny. CaptionDoor excludes identification, profiling, autonomous reception, and recording. Provider/backup deletion limits must be disclosed; no success claim may conceal pending deletion.

## DynamoDB

The [transaction contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html) permits up to 100 distinct-item actions and 4 MB per atomic transaction in one account/Region. Two actions cannot target the same item: put the condition on the Update instead of pairing ConditionCheck and Update. GSI/Streams propagation can interleave transaction records. Application idempotency items outlive the API's short client-token window; do not rely on stream transaction grouping.

The [read consistency contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) supports strong reads on base tables/LSIs, not GSIs or Streams. Authorize and resolve conflicts from strongly read base items. GSI lookup is discovery only; recheck authoritative items.

The [TTL contract](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html) uses numeric epoch seconds and delayed cleanup, usually days. Expired items can still exist and be modified. Enforce application expiry before reads, writes and socket operations; explicit deletion jobs remove content, TTL is a backstop.

The [Lambda/Streams contract](https://docs.aws.amazon.com/lambda/latest/dg/with-ddb.html) is at least once and can duplicate records. Use idempotent dispatch, partial batch responses and bounded retries. CaptionDoor's cloud transport design is KEYS_ONLY Runtime job inserts → filtered Lambda → SQS containing job keys → Node worker. Local due-index polling exercises the same durable handler but does **not** validate AWS Streams, Lambda or SQS transport. The persistent job and due GSI recover missed dispatch; Streams is not a permanent queue.

## Transcribe and audio

[Streaming input](https://docs.aws.amazon.com/transcribe/latest/dg/streaming.html) supports signed PCM16 little-endian (not WAV), FLAC, or Opus in Ogg; recommends uniform 50–200 ms chunks and an accurate sampling rate. CaptionDoor selects incoming remote audio only, resamples to mono 16 kHz and sends 100 ms PCM chunks (3,200 bytes). No resident microphone, WAV headers or WebM relabeling. An AWS stream requires credentials/Region and `transcribe:StartStreamTranscription`; the local fixture is separately labeled.

[Partial results](https://docs.aws.amazon.com/transcribe/latest/dg/streaming-partial-results.html) revise during recognition; `IsPartial=false` denotes final segments, not verified truth. CaptionDoor replaces by `(mediaSessionId, ResultId)`, retains offsets/source and persists only finals once. No invented speaker/confidence, no language-model rewriting. Disconnect/lease loss stops the stream and discards delayed buffered audio.

## Pre-smoke failure handling (2026-10-22 UTC)

Local mocked regressions now reject empty/control-character tokens and unsafe expiry values, sanitize malformed token JSON, and clean up a trusted WHEP Location when its created session has an unreadable/invalid answer. Cleanup failure is explicitly unconfirmed, never successful; no credential is sent to an untrusted Location. Browser callbacks refuse LIVE/audio delivery after lease expiry, and negotiation rechecks cancellation/expiry after applying remote SDP before returning a controller or installing timers. The provider lease starts conservatively before POST, so signaling latency cannot extend the advertised30/60-second limit. These are fixture tests, not observed Ring/WebRTC behavior. The WHEP docs do not prescribe one DELETE success status; mocked 200 and 204 responses exercise ordinary successful HTTP handling without claiming a provider observation. For an invalid-answer session whose immediate cleanup fails, no durable media record has yet been returned to the caller; the failure is reported and provider termination remains unobserved, subject to documented session limits.

## Required outbound headers — October 22 focused fix

The [current required-header contract](https://developer.amazon.com/docs/ring/api-documentation.html#required-http-headers) applies to Ring API and OAuth calls: application/version User-Agent and UUID Hardware_Id per user/device combination. The adapter now sends `CaptionDoor/0.1.0` and requires an explicit persisted UUID for both transports. It cannot invent a global or per-request fallback. Trusted server operations establish nonsecret client metadata before an authorized external operation; no credentials or real Ring request were created by this fix. OAuth binding, refresh and bounded encrypted WHEP cleanup retain the same identity.

The backend device interpretation is the configured canonical origin scoped to the linking resident. This is an implementation assumption needing Ring confirmation, not evidence of provider acceptance. Existing linked rows without identity fail closed rather than silently using credentials.
